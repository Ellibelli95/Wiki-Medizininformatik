Server

Dieser Wiki-Artikel ist als technische Wissensseite für Server vorgesehen.

Dokumentationsstruktur: Grundlagen · Komponenten · technische Funktionsweise · Konfiguration · Datenfluss · Schnittstellen · Sicherheit · Fehleranalyse · Praxisbeispiele.

Grundlagen

Ein Server ist ein Rechnersystem, das Dienste (Anwendungen, Daten, Kommunikationsfunktionen) über das Netzwerk für andere Systeme oder Nutzende bereitstellt. In der Krankenhaus-IT laufen auf Servern u. a. das KIS, PDMS, PACS, Datenbanken, Kommunikations-/Interface-Server für die Medizingerätevernetzung sowie Basisdienste wie Verzeichnisdienst (Active Directory), DHCP/DNS und Monitoring. Server sind physisch im Rechenzentrum untergebracht und laufen heute überwiegend als virtualisierte Instanzen statt auf dedizierter Einzelhardware.

Komponenten

  • Physische Serverhardware – Rackserver oder Blade-Systeme mit CPU, Arbeitsspeicher, lokalem oder angebundenem Storage, redundanten Netzteilen und Netzwerkkarten.
  • Betriebssystem – z. B. Windows Server oder Linux-Distributionen, Grundlage für die darauf laufenden Dienste.
  • Serverrollen/-dienste – Applikationsserver (z. B. KIS-Anwendungslogik), Datenbankserver, Kommunikations-/Interface-Server (HL7-Nachrichtenverarbeitung), Webserver, Verzeichnisdienst.
  • Management-/Out-of-Band-Zugang – z. B. iDRAC/iLO, ermöglicht Fernwartung auch bei nicht laufendem Betriebssystem.

Technische Funktionsweise

Server nehmen über das Netzwerk Anfragen entgegen (z. B. HL7-Nachrichten von einem Gateway, HTTP-Anfragen eines Web-Clients, Datenbankabfragen einer Anwendung), verarbeiten diese gemäß der installierten Dienste und liefern Ergebnisse zurück. Mehrere logische Dienste können auf einem physischen Server oder – heute Standard – auf virtuellen Maschinen (siehe Virtualisierung) gebündelt werden, was Auslastung und Verwaltung effizienter macht als ein physischer Server pro Dienst ("ein Server für alles" vs. "ein Server pro Anwendung" als klassischer Zielkonflikt, den Virtualisierung auflöst).

Konfiguration

  • Rollenverteilung planen: welche Dienste auf welchem (virtuellen) Server laufen, unter Berücksichtigung von Ressourcenbedarf und Abhängigkeiten.
  • Patch- und Update-Management mit Wartungsfenstern, die auf den klinischen Betrieb abgestimmt sind (viele Systeme sind 24/7 im Einsatz).
  • Ressourcenzuteilung (CPU, RAM, Storage-Performance) je nach Kritikalität und Lastprofil des jeweiligen Dienstes.
  • Namens- und Adresskonventionen sowie zentrale Dokumentation (Inventar/CMDB) für alle produktiven Server.

Datenfluss

Ein Server empfängt Anfragen über seine Netzwerkschnittstelle, verarbeitet sie in der zuständigen Anwendungsschicht (z. B. Interface Engine, KIS-Kernanwendung) und greift dabei häufig auf eine Datenbank zu, bevor eine Antwort zurückgesendet wird. In der Gerätevernetzung endet der in den Vernetzungsseiten beschriebene Datenfluss (Gerät → Switch → Segment → Gateway) typischerweise genau an einem solchen Server.

Schnittstellen

Server stellen ihre Dienste über standardisierte Schnittstellen bereit: HL7/FHIR-Endpunkte für klinische Kommunikationsserver, SQL/ODBC für Datenbankzugriffe, HTTP(S)/REST für Webanwendungen, SMB/NFS für Dateifreigaben. Verwandte Themen: Standards, KIS & Systeme.

Sicherheit

  • Härtung des Betriebssystems (Deaktivierung nicht benötigter Dienste, restriktive lokale Firewall) reduziert die Angriffsfläche.
  • Zugriff auf Serverbetriebssysteme und Management-Interfaces nur für berechtigtes Administrationspersonal, mit personalisierten Konten statt geteilter Zugänge.
  • Regelmäßiges Patchen bekannter Schwachstellen – bei Servern mit hoher Verfügbarkeitsanforderung koordiniert mit Wartungsfenstern und ggf. vorheriger Testumgebung.
  • Weiterführende, systemübergreifende Sicherheitsmaßnahmen siehe Security.

Fehleranalyse

  • Dienst auf Server nicht erreichbar: zunächst grundlegende Netzwerkerreichbarkeit (Ping) prüfen, dann Dienststatus auf dem Server selbst kontrollieren.
  • Hohe Antwortzeiten: CPU-/RAM-/Storage-Auslastung des Servers sowie Datenbank-Performance prüfen – oft über das zentrale Monitoring ersichtlich.
  • Dienst startet nach Neustart nicht automatisch: Konfiguration des automatischen Dienststarts sowie Abhängigkeiten zu anderen Diensten (z. B. Datenbank muss vor Applikationsserver starten) prüfen.
  • Wiederkehrende Abstürze: Systemlogs auf Hardwarefehler, Speicherprobleme oder Softwarekonflikte auswerten.

Praxisbeispiele

  • Kommunikationsserver für Patientenmonitore: nimmt HL7-Nachrichten der Gateways entgegen, reichert sie um Patientenkontext an und leitet sie ans PDMS weiter.
  • Konsolidierung mehrerer Altserver: mehrere bislang auf Einzelhardware betriebene Dienste werden als virtuelle Maschinen auf weniger physischen Servern zusammengeführt, um Wartungsaufwand und Energiebedarf zu senken.
  • Geplantes Wartungsfenster: Patcheinspielung auf einem Applikationsserver außerhalb der Kernbetriebszeiten, mit vorherigem Failover auf eine redundante Instanz (siehe Hochverfügbarkeit).
