Virtualisierung

Dieser Wiki-Artikel ist als technische Wissensseite für Virtualisierung vorgesehen.

Dokumentationsstruktur: Grundlagen · Komponenten · technische Funktionsweise · Konfiguration · Datenfluss · Schnittstellen · Sicherheit · Fehleranalyse · Praxisbeispiele.

Grundlagen

Virtualisierung ermöglicht es, mehrere logisch getrennte virtuelle Maschinen (VMs) auf einer gemeinsamen physischen Server-Hardware zu betreiben. Statt für jeden Dienst (KIS-Anwendungsserver, Datenbank, Kommunikationsserver) einen eigenen physischen Server vorzuhalten, teilen sich mehrere VMs die vorhandenen Ressourcen eines physischen Hosts. Im Krankenhausumfeld ist Virtualisierung heute Standard, da sie Hardware effizienter nutzt, Bereitstellung neuer Server stark beschleunigt und die Grundlage für viele Hochverfügbarkeits-Mechanismen bildet (z. B. Live-Migration einer VM bei drohendem Hardwareausfall).

Komponenten

  • Hypervisor – Software-Schicht, die die physische Hardware abstrahiert und mehreren VMs gleichzeitig Zugriff darauf ermöglicht (z. B. VMware ESXi, Microsoft Hyper-V, KVM).
  • Virtuelle Maschinen (VMs) – logisch eigenständige Server mit eigenem Betriebssystem, isoliert von anderen VMs auf demselben Host.
  • Virtuelle Netzwerke/Switches – softwaredefinierte Netzwerkverbindungen zwischen VMs und zum physischen Netzwerk.
  • Shared Storage (SAN/NAS) – zentraler Speicher, auf den mehrere Hypervisor-Hosts zugreifen, Voraussetzung für Live-Migration von VMs zwischen Hosts.
  • Verwaltungsplattform – zentrale Konsole zur Steuerung aller Hosts und VMs (z. B. VMware vCenter).

Technische Funktionsweise

Der Hypervisor läuft entweder direkt auf der Hardware (Typ 1, "Bare-Metal", üblich in Rechenzentren) oder auf einem bestehenden Betriebssystem (Typ 2, eher für Einzelplatzsysteme). Er teilt physische Ressourcen (CPU-Kerne, Arbeitsspeicher, Netzwerk- und Storage-Zugriff) den einzelnen VMs zu und isoliert sie voneinander, sodass ein Problem in einer VM die anderen nicht direkt beeinträchtigt. Über Shared Storage und ein Cluster mehrerer Hypervisor-Hosts lässt sich eine VM im laufenden Betrieb ohne spürbare Unterbrechung von einem Host auf einen anderen verschieben (Live-Migration) – etwa vor einer geplanten Hardwarewartung.

Konfiguration

  • Ressourcenzuteilung je VM (vCPU, RAM, Storage) passend zum tatsächlichen Bedarf des jeweiligen Dienstes dimensionieren – Überprovisionierung kann bei Lastspitzen zu Engpässen führen.
  • Cluster mehrerer Hosts mit Shared Storage einrichten, um Live-Migration und automatisches Failover bei Hostausfall zu ermöglichen.
  • Snapshots vor risikobehafteten Änderungen (Updates, Konfigurationsänderungen) erstellen, um bei Problemen schnell zurückzurollen.
  • Ressourcenreserven für Ausfallszenarien einplanen (N+1-Prinzip: genug freie Kapazität, damit bei Ausfall eines Hosts dessen VMs auf den verbleibenden Hosts weiterlaufen können).

Datenfluss

Netzwerkverkehr einer VM läuft über den virtuellen Switch des Hypervisors zum physischen Netzwerkadapter des Hosts und von dort ins reguläre Netzwerk – für andere Systeme ist eine VM im laufenden Betrieb nicht von einem physischen Server unterscheidbar. Speicherzugriffe erfolgen meist über das Shared Storage, unabhängig davon, auf welchem physischen Host die VM aktuell läuft.

Schnittstellen

Virtualisierungsplattformen bieten APIs zur Automatisierung (z. B. automatisches Bereitstellen neuer VMs), Schnittstellen zum Storage-System (z. B. iSCSI, Fibre Channel) sowie Integration mit dem zentralen Monitoring, um Ressourcenauslastung und Hoststatus zu überwachen.

Sicherheit

  • Der Hypervisor selbst ist eine kritische Angriffsfläche: Zugriff auf die Verwaltungsplattform streng auf autorisiertes Administrationspersonal beschränken, idealerweise über ein separates Management-Netz.
  • Isolation zwischen VMs ist grundsätzlich hoch, aber nicht absolut – bekannte Hypervisor-Schwachstellen ("VM Escape") erfordern konsequentes Patchen der Virtualisierungsplattform.
  • Snapshots und VM-Images enthalten vollständige Systemzustände inkl. ggf. sensibler Daten – entsprechend geschützt und nicht unkontrolliert kopierbar aufbewahren.

Fehleranalyse

  • VM reagiert langsam: Ressourcenauslastung der VM selbst sowie Gesamtauslastung des physischen Hosts prüfen (Ressourcenkonkurrenz mit anderen VMs möglich).
  • Live-Migration schlägt fehl: Kompatibilität der CPU-Features zwischen Quell- und Zielhost sowie Erreichbarkeit des Shared Storage von beiden Hosts kontrollieren.
  • VM startet nach Hostausfall nicht automatisch neu: Konfiguration der automatischen Failover-/HA-Funktion der Virtualisierungsplattform prüfen.
  • Speicherplatzprobleme trotz ausreichend zugewiesenem virtuellem Storage: tatsächliche Belegung auf dem zugrunde liegenden Shared Storage sowie angesammelte Snapshots prüfen.

Praxisbeispiele

  • Geplante Hardwarewartung eines Hosts: alle darauf laufenden VMs werden per Live-Migration auf andere Hosts im Cluster verschoben, Wartung erfolgt ohne Unterbrechung der klinischen Anwendungen.
  • Testumgebung für ein KIS-Update: Snapshot des produktiven Anwendungsservers wird als isolierte Test-VM bereitgestellt, um das Update risikofrei zu prüfen, bevor es produktiv eingespielt wird.
  • Ausfall eines physischen Hosts: Cluster erkennt den Ausfall automatisch und startet die betroffenen VMs auf den verbleibenden Hosts neu, sodass Dienste nach kurzer Unterbrechung wieder verfügbar sind.
