Interface Engine

Dieser Artikel betrachtet den im Kommunikationsserver-Artikel bereits als Betriebs- und Netzwerkrolle beschriebenen Baustein aus der Software- und Integrations-Perspektive: Welche Entwurfsmuster liegen jeder Interface Engine zugrunde, welche konkreten Produkte gibt es am Markt, und wie lässt sich die Integrationskomplexität in einer wachsenden Systemlandschaft beherrschbar halten?

① Grundlagen

Eine Interface Engine (Integration Engine) ist Middleware-Software, die Nachrichten zwischen heterogenen Systemen entgegennimmt, transformiert und weiterleitet. Der Kommunikationsserver-Artikel beschreibt bereits ausführlich, welche Aufgabe diese Software im Kliniknetz übernimmt und zeigt mit Mirth Connect ein konkretes Produktbeispiel. Dieser Artikel ergänzt die dahinterliegenden Entwurfsprinzipien.

② Integrationsmuster

Interface Engines setzen typischerweise wiederkehrende Entwurfsmuster der Enterprise-Integration um:

MusterBeschreibung
Message RouterLeitet eine Nachricht anhand einer Regel an das passende Zielsystem weiter
Content-Based RouterTrifft die Routing-Entscheidung anhand des Nachrichteninhalts, z. B. Nachrichtentyp ADT vs. ORU
Message TranslatorWandelt ein Nachrichtenformat in ein anderes um (z. B. HL7 v2 in FHIR)
Publish-SubscribeEin Sender veröffentlicht eine Nachricht, beliebig viele interessierte Systeme empfangen sie, ohne dass der Sender sie einzeln kennen muss

Diese Muster entsprechen genau den im Kommunikationsserver-Artikel beschriebenen Mirth-Connect-Bausteinen Source Connector, Filter/Transformer und Destination Connector.

③ Canonical Data Model

In größeren Kliniken mit vielen Systemen wächst der Aufwand für direktes Punkt-zu-Punkt-Mapping quadratisch mit der Anzahl der Systeme (siehe Abb. 1, links). Das Canonical Data Model löst dieses Problem: Jedes System mappt nur einmal auf ein gemeinsames, neutrales Zwischenformat (z. B. FHIR-Ressourcen) – die Interface Engine übernimmt die Übersetzung zwischen diesem Zwischenformat und jedem angeschlossenen System. Statt n·(n-1) Mappings sind dann nur noch n Mappings nötig.

④ Marktüberblick

Neben dem bereits vorgestellten Mirth Connect (NextGen Connect) sind im Klinikumfeld u. a. folgende Interface-Engine-Produkte verbreitet – rein zur fachlichen Einordnung, ohne Wertung:

ProduktBesonderheit
Mirth Connect / NextGen ConnectQuelloffen, weit verbreitet, channel-basierte Architektur (siehe Kommunikationsserver-Artikel)
InterSystems Ensemble / HealthShareKombiniert Interface-Engine-Funktionen mit einer eigenen Datenplattform
Rhapsody Integration EngineGrafische Konfiguration von Nachrichtenflüssen, verbreitet in Radiologie-/Laborumgebungen
Cloverleaf (Infor)Langjährig etabliert in großen Krankenhausverbünden

⑤ Monitoring und Fehleranalyse

  • Nachrichtenverfolgung: Jede Interface Engine protokolliert Empfang, Transformation und Zustellung jeder einzelnen Nachricht.
  • Audit-Trail: Zugriffe und Änderungen an Routing-Regeln werden nachvollziehbar protokolliert (siehe auch ATNA im IHE-Artikel).
  • Alarmierung: Ausbleibende Bestätigungen (ACK-Timeouts) lösen automatisch Warnungen an die IT aus.

⑥ Praxisbeispiel: Neues System per Canonical Model anbinden

Das Klinikum integriert eine neue Reha-Einrichtungssoftware in die bestehende Systemlandschaft aus KIS, RIS, LIS und PACS.

  1. Ohne Canonical Model müsste die neue Software einzeln an KIS, RIS, LIS und PACS angebunden werden – vier separate Mappings.
  2. Mit Canonical Model entwickelt das Integrationsteam nur ein einziges Mapping: von der Reha-Software auf das bereits etablierte, gemeinsame Zwischenformat.
  3. Die Interface Engine übernimmt automatisch die bereits vorhandene Übersetzung vom Zwischenformat zu KIS, RIS, LIS und PACS – diese Mappings existierten bereits für alle anderen Systeme.
  4. Die neue Reha-Software kann dadurch mit einem Bruchteil des Integrationsaufwands produktiv gehen, den eine Punkt-zu-Punkt-Anbindung erfordert hätte.
Ergebnis für die Praxis: Der Vorteil eines Canonical Data Models zeigt sich erst bei wachsender Systemlandschaft – bei zwei Systemen ist der Unterschied gering, bei zehn oder mehr Systemen entscheidet er darüber, ob die Integration neuer Software Tage oder Monate dauert.
