1. Was ist REST?

AspektBeschreibung
DefinitionREST (Representational State Transfer) ist ein von Roy Fielding beschriebener Architekturstil für verteilte Systeme, der insbesondere für Web-APIs auf Basis von HTTP verbreitet ist.
GrundideeDaten werden als adressierbare Ressourcen modelliert, auf die über eine einheitliche Schnittstelle mit Standard-HTTP-Methoden zugegriffen wird.
AbgrenzungREST ist kein Protokoll und kein Standard im engeren Sinne, sondern eine Sammlung von Architekturprinzipien, an denen sich eine API orientieren kann.

2. REST-Prinzipien

PrinzipBeschreibung
Zustandslosigkeit (Stateless)Jede Anfrage enthält alle für ihre Bearbeitung notwendigen Informationen; der Server hält keinen Sitzungszustand zwischen Anfragen vor.
Einheitliche SchnittstelleRessourcen werden über URIs adressiert und mit einer festen Menge an HTTP-Methoden einheitlich manipuliert.
Client-Server-TrennungClient und Server sind unabhängig voneinander entwickelbar, solange die Schnittstelle stabil bleibt.
CacheabilityAntworten können als cachebar oder nicht cachebar gekennzeichnet werden, um Performance zu verbessern.
Layered SystemZwischen Client und eigentlichem Server können weitere Schichten (z. B. Load Balancer, Gateway) eingefügt werden, ohne dass der Client dies bemerkt.

3. Ressourcen und URIs

AspektBeispiel
RessourceEin Patient, eine Messung, ein Termin – jede fachliche Entität wird als Ressource betrachtet.
Kollektions-URI/patienten adressiert die Gesamtheit aller Patienten.
Einzel-Ressourcen-URI/patienten/123 adressiert genau einen Patienten mit der ID 123.
NamenskonventionURIs sollten Substantive statt Verben verwenden, da die Aktion bereits durch die HTTP-Methode ausgedrückt wird.

4. HTTP-Methoden

MethodeCRUD-BedeutungEigenschaft
GETRead (Lesen)Sicher (verändert keinen Zustand) und idempotent
POSTCreate (Erzeugen)Nicht idempotent; wiederholtes Senden kann mehrfach Ressourcen anlegen
PUTUpdate/Replace (vollständiges Ersetzen)Idempotent; mehrfaches Senden derselben Anfrage führt zum selben Endzustand
PATCHUpdate (Teilaktualisierung)Verändert nur die übergebenen Felder einer Ressource
DELETEDelete (Löschen)Idempotent; wiederholtes Löschen einer bereits gelöschten Ressource ändert nichts weiter

5. HTTP-Statuscodes

KlasseBedeutungBeispiel
2xxErfolgreiche Verarbeitung200 OK, 201 Created, 204 No Content
3xxWeiterleitung301 Moved Permanently, 304 Not Modified
4xxClient-Fehler400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xxServer-Fehler500 Internal Server Error, 503 Service Unavailable

6. Repräsentationen: JSON versus XML

FormatMerkmal
JSONKompaktes, leicht lesbares Textformat (siehe Kapitel „JSON“); heutiger De-facto-Standard für REST-APIs.
XMLAusführlicheres, strenger strukturiertes Format mit Schemavalidierung; historisch bei SOAP-Diensten dominant, in modernen REST-APIs seltener.
Content-NegotiationÜber den HTTP-Header Accept kann der Client das gewünschte Antwortformat anfragen.

7. Richardson-Reifegradmodell

LevelBeschreibung
Level 0Ein einziger Endpunkt, über den alle Operationen per POST abgewickelt werden (RPC-artig, kaum REST-Prinzipien).
Level 1Einführung mehrerer Ressourcen-URIs, aber weiterhin überwiegend einheitliche HTTP-Methode.
Level 2Konsequente Nutzung der passenden HTTP-Methoden (GET/POST/PUT/DELETE) und Statuscodes je Ressource – in der Praxis am häufigsten anzutreffen.
Level 3Zusätzlich Hypermedia-Steuerung (HATEOAS): Antworten enthalten Links auf mögliche Folgeaktionen.

8. REST versus SOAP

AspektRESTSOAP
GrundprinzipArchitekturstil auf Basis von HTTP und RessourcenProtokoll mit striktem XML-Nachrichtenformat
FormatMeist JSON, auch XML möglichAusschließlich XML nach festem Envelope-Schema
KomplexitätGeringer, leichter verständlichHöher, mit umfangreichen Zusatzstandards (WS-*)
Typischer EinsatzModerne Web- und Mobile-APIsÄltere Enterprise-Integrationen mit hohen Transaktionsanforderungen

9. REST in Node.js und Express

KonzeptBeschreibung
Node.jsJavaScript-Laufzeitumgebung außerhalb des Browsers, häufig für performante, ereignisgesteuerte Server eingesetzt.
Express.jsSchlankes Webframework für Node.js zur Definition von Routen und Middleware.
RoutingEndpunkte werden über Kombinationen aus HTTP-Methode und Pfad definiert, z. B. app.get('/patienten/:id', handler).
EinordnungNode.js, Express und eine Dokumentendatenbank (z. B. MongoDB) bilden zusammen mit einem Frontend-Framework wie Angular den sogenannten MEAN-Stack.

10. REST in der Medizin-IT

AspektBeschreibung
HL7 FHIRDefiniert Gesundheitsdaten als RESTful-Ressourcen (z. B. Patient, Observation) mit standardisierten Operationen.
Integration heterogener SystemeRESTful-Schnittstellen erleichtern die Anbindung unterschiedlicher Hersteller-Systeme an KIS/PDMS (siehe Kapitel „Gerätevernetzung“).
SkalierbarkeitDie Zustandslosigkeit von REST erleichtert die horizontale Skalierung von Applikationsservern im Rechenzentrum.

11. Sicherheit von REST-APIs

MaßnahmeBeschreibung
HTTPS/TLSVerschlüsselte Übertragung zum Schutz vor Abhören und Manipulation.
Token-Authentifizierung (JWT)Da REST-APIs zustandslos sind, wird die Authentifizierung meist über ein bei jeder Anfrage mitgesendetes Token realisiert (siehe Kapitel „APIs“, Abschnitt 7, und „Web Security“).
Rate LimitingBegrenzung der Anfragehäufigkeit pro Client zum Schutz vor Missbrauch und Überlastung.
EingabevalidierungServerseitige Prüfung aller übermittelten Daten, unabhängig von einer eventuell bereits erfolgten clientseitigen Validierung.
